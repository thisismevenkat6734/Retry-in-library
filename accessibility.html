ACCESS FOR EVERY LEARNER

Accessibility

Our goal is to make learning resources easier to access and use across different devices and abilities.

Accessibility commitment and current status

RETRY IN LIBRARY aims to improve accessibility using recognised web accessibility practices, including WCAG 2.1 Level AA as a development target. This is a target, not a claim of certified compliance. The website has not yet undergone a complete independent accessibility audit.

1. Our Accessibility Goals

We want students to be able to read, navigate and use learning resources with different devices, input methods and assistive technologies.

  • Clear and readable page structure.
  • Keyboard-friendly navigation and controls.
  • Meaningful headings and page landmarks.
  • Readable text and sufficient colour contrast.
  • Useful labels for interactive controls.
  • Responsive layouts for mobile, tablet and desktop.
  • Support for Telugu and English educational content.

2. Keyboard Navigation

We aim to make important website features usable without requiring a mouse or touchscreen.

  • Use the Tab key to move between interactive elements.
  • Use Shift + Tab to move backwards.
  • Use Enter or Space to activate supported controls.
  • Use the Skip to Content link to reach the main content quickly.

Keyboard behaviour may vary by browser and device. Any inaccessible control should be reported for review.

3. Screen Readers and Assistive Technology

We aim to use semantic HTML, descriptive link text, accessible form labels and meaningful page titles.

These practices can help screen readers and other assistive technologies interpret page content.

Compatibility can vary between browsers, operating systems and assistive technologies. Full compatibility has not yet been independently verified.

4. Telugu and English Learning Content

The project is intended to provide educational material in Telugu and English.

We aim to use readable Telugu text, appropriate language labels and clear separation between Telugu and English explanations.

Some pages or resources may not yet be fully translated. Language availability should be checked on each page.

5. Colour, Text and Readability

We aim to use readable font sizes, clear visual hierarchy and adequate contrast between text and backgrounds.

Users may also be able to use browser zoom and device-level accessibility settings.

Colour should not be the only way important information is communicated.

6. Mobile and Responsive Access

The website is designed to adapt to different screen sizes. We aim to make reading, navigation and practice features usable on mobile devices as well as larger screens.

Device, browser and network limitations may affect individual experiences.

7. Known Limitations

Some accessibility issues may remain while the website is under development. Examples may include:

  • Older PDF documents that are not screen-reader friendly.
  • Images or diagrams with incomplete alternative text.
  • Third-party websites outside our control.
  • Content that has not yet been fully translated.
  • Interactive features that require additional keyboard or screen-reader testing.

We aim to identify and improve these issues as the project develops.

8. Accessibility Feedback

If you face a difficulty accessing a page or using a feature, please note:

  • The page URL.
  • The device and browser you are using.
  • The feature or content that caused difficulty.
  • The assistive technology used, if relevant.
  • What you were trying to do and what happened instead.

Please avoid sharing unnecessary sensitive personal information.

A verified public accessibility contact channel has not yet been published. The Contact page currently does not provide an active accessibility feedback submission form.

9. Continuous Improvement

Accessibility should be reviewed throughout development, not only after launch.

Planned checks include keyboard testing, screen-reader testing, colour contrast checks, mobile layout testing, form-label checks and automated accessibility scans.

Automated tools alone cannot establish full accessibility compliance. Manual testing is also necessary.
